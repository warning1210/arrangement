01

로그인 시도 제한 — IP 기준 Rate Limit

LoginRateLimitFilter.java
문제 사항

Turnstile을 한 번 통과한 뒤에도, 같은 사람(또는 같은 세션)이 로그인 API 자체는 무제한으로 반복 호출할 수 있었다.

문제 사항 분석 — Turnstile은 "이 요청을 사람이 보냈는가"만 판별할 뿐, 그 사람이 같은 아이디에 비밀번호를 계속 바꿔가며 넣어보는 것까지는 막지 못한다. 로그인 API(/api/hq-auth/login, /api/branch-auth/db-login, /api/branch-auth/firebase-session) 자체에는 시도 횟수 제한이 전혀 없었다.

  • Turnstile 통과 이후에도 무차별 대입(brute-force)이 계속 가능
  • 계정 단위 잠금 없이, 같은 IP에서 짧은 시간에 쏟아지는 요청 자체를 걸러낼 장치가 없었음
해결 방안

서블릿 필터 하나(LoginRateLimitFilter)로 로그인류 POST 엔드포인트 3개를 클라이언트 IP 기준 5분당 10회로 제한한다. 컨트롤러·로그인 서비스보다 앞단에서 걸러지므로, 임계치를 넘으면 Turnstile 검증이나 비밀번호 대조까지 갈 필요도 없이 즉시 차단된다.

  • ConcurrentHashMap<IP, AtomicReference<Window>>로 인메모리 카운팅 — DB나 별도 캐시 없이 updateAndGet으로 원자적으로 증가·리셋
  • 5분 윈도우 안에서 11번째 요청부터 HTTP 429 + {"message":"요청이 너무 많습니다. 잠시 후 다시 시도해주세요."} 응답
  • @Component로 등록된 Filter 빈을 Spring Boot가 서블릿 컨테이너에 자동 등록 — SecurityConfig에 별도 설정을 추가할 필요가 없음
backend/.../global/security/LoginRateLimitFilter.javaJava
private static final Set<String> LIMITED_PATHS = Set.of(
    "/api/hq-auth/login",
    "/api/branch-auth/db-login",
    "/api/branch-auth/firebase-session"
);
private static final int MAX_ATTEMPTS = 10;
private static final Duration WINDOW = Duration.ofMinutes(5);

private record Window(int count, Instant resetAt) {}

// IP별로 윈도를 원자적으로 갱신 — 윈도가 지났으면 1로 리셋, 아니면 +1
Window updated = ref.updateAndGet(w -> Instant.now().isAfter(w.resetAt())
    ? new Window(1, Instant.now().plus(WINDOW))
    : new Window(w.count() + 1, w.resetAt()));

if (updated.count() > MAX_ATTEMPTS) {
  response.setStatus(429);
  response.getWriter().write("{\"message\":\"요청이 너무 많습니다. 잠시 후 다시 시도해주세요.\"}");
  return;
}

현재 구현의 제약

계정이 아니라 IP 단위로만 제한한다 — 같은 매장 공유기 뒤에 여러 키오스크가 물려 있을 수 있어 매장 전체가 한 번에 묶이지 않도록 임계치를 넉넉하게(5분당 10회) 잡았지만, 반대로 특정 계정만 노려 낮은 빈도로 시도하는 공격은 막지 못한다.

카운터가 인메모리(ConcurrentHashMap)라 앱을 재시작하면 초기화되고, 인스턴스를 여러 대 띄우면 인스턴스별로 따로 카운트된다. IP도 request.getRemoteAddr()를 그대로 쓰기 때문에, 리버스 프록시 뒤에 배포한다면 프록시 IP로 요청이 뭉치지 않도록 X-Forwarded-For 처리가 추가로 필요하다.

프론트엔드에는 429를 따로 구분해 처리하는 코드가 없다 — BranchLoginView.vue는 이 응답도 다른 로그인 실패와 동일하게 error.response.data.message로 표시하고 Turnstile 위젯을 리셋한다. 실제로는 토큰을 소모한 게 아니라서 위젯을 되돌릴 필요는 없지만, 공통 에러 처리 경로를 그대로 타면서 생기는 사소한 부정확함이다.

02

Turnstile 캡차 — 사람인지 검증

BranchLoginView.vue TurnstileVerifier.java HqAuthService.java BranchAuthService.java BranchFallbackLoginService.java
문제 사항

로그인 API가 자동화된 요청에 그대로 노출되어 있었다.

문제 사항 분석 — 로그인 폼은 아이디·비밀번호 형식만 확인할 뿐, "이 요청을 사람이 보냈는가"를 확인하는 절차가 전혀 없었다. 브라우저를 거치지 않고 API를 직접 호출해도 동일하게 처리되는 구조였다.

  • 무차별 대입(brute-force): 비밀번호 조합을 자동으로 반복 시도할 수 있음
  • 자격증명 스터핑(credential stuffing): 다른 서비스에서 유출된 아이디·비밀번호 목록을 대량으로 대입 가능
  • 클라이언트(JS) 레벨 검증만으로는 위조 가능 — 서버가 직접 확인하지 않으면 신뢰할 수 없음
해결 방안

Cloudflare Turnstile을 붙여, 로그인 API가 실제 인증(비밀번호/Firebase 토큰 검증)을 수행하기 전에 서버가 "사람인지"를 직접 재확인하도록 만들었다.

  • 위젯이 발급한 토큰을 프론트가 각 로그인 요청 본문에 turnstileToken 필드로 실어 백엔드로 전달
  • TurnstileVerifier가 그 토큰을 들고 Cloudflare 서버에 siteverify로 재검증 (서버-서버 통신이라 위조 불가)
  • HqAuthService.login() / BranchAuthService.firebaseSession() 각각의 첫 줄에서 실제 인증 로직 이전에 호출
  • 검증 실패 시 위젯을 리셋해 사용자가 다시 시도할 수 있게 처리

구현 상세 — 5단계 흐름

캡차는 "이 요청을 사람이 보냈는가"를 확인하는 절차다. 자바스크립트가 하는 판단은 위조하기 쉬우므로, 반드시 서버가 Cloudflare 서버에 직접 물어봐야 신뢰할 수 있다.

1

위젯이 그려진다

로그인 화면이 마운트되면 BranchLoginView.vue가 Cloudflare 스크립트를 직접 <head>에 주입하고, 로드가 끝나면 window.turnstile.render()로 위젯을 그린다. 사용자는 체크박스를 누르거나, 위험도가 낮다고 판단되면 자동으로 통과된다.

브라우저 · BranchLoginView.vue
2

토큰이 발급된다

통과하면 위젯이 긴 문자열 토큰을 callback으로 넘겨주고, turnstileToken 상태에 저장된다.

브라우저 · BranchLoginView.vue
3

토큰을 로그인 요청에 실어 보낸다

별도의 사전 검증 API 없이, /hq-auth/login · /branch-auth/firebase-session · /branch-auth/db-login 요청 본문에 turnstileToken을 그대로 함께 담아 보낸다.

프론트 → 백엔드 · BranchLoginView.vue
4

서버가 Cloudflare에 되묻는다

각 로그인 서비스 메서드의 첫 줄에서 TurnstileVerifier.verify(token)이 비밀키 + 받은 토큰을 Cloudflare의 siteverify API로 서버-서버 통신한다. 이 단계가 신뢰의 핵심이다.

백엔드 → Cloudflare · TurnstileVerifier.java
5

통과/거절을 로그인 흐름에 반영한다

검증에 실패하면 IllegalArgumentException이 던져져 실제 인증 로직(비밀번호 대조 등)까지 가지 않고 즉시 끝난다. 프론트는 실패 시 위젯을 리셋하고 에러 메시지를 띄운다.

토큰 재사용 문제가 다시 나타날 수 있는 구조

이 로그인 폼은 아이디 하나만으로 본사 계정인지 지점 계정인지 미리 알 수 없어서, loginAsHq를 먼저 시도하고 실패하면 loginWithFirebase 또는 loginWithDb를 이어서 시도한다 — 이때 같은 turnstileToken 값을 두 번째 요청에도 그대로 재사용한다.

그런데 Cloudflare Turnstile 토큰은 siteverify로 한 번 검증되는 순간 폐기되는 값이라, 이메일로 로그인하는 지점 관리자의 경우 1차 시도(loginAsHq → 실패)에서 토큰이 이미 소모되고, 2차 시도(loginWithFirebase)의 TurnstileVerifier.verify()가 같은 토큰을 다시 Cloudflare에 보내면서 "이미 사용된 토큰"으로 거절될 가능성이 있다 — 아이디·비밀번호가 맞아도 로그인이 실패할 수 있는 구조다. 과거 버전(구 보안 기능 리스트.html)에서는 이 문제를 "검증을 시도 루프 바깥에서 딱 한 번만" 수행하는 방식으로 해결했었는데, 지금 구조로 리팩터링되며 그 안전장치가 사라진 것으로 보인다.

로컬에서 체크박스를 강제로 띄우는 법

Turnstile은 위험도가 낮은 트래픽이면 체크박스 없이 조용히 통과시키는 적응형(adaptive) 방식이라, 로컬 개발 환경에서는 거의 항상 자동 통과된다 — 버그가 아니라 사용자 마찰을 줄이기 위한 의도된 동작이다. 체크박스 UI를 눈으로 확인하려면 Cloudflare가 제공하는 더미 테스트 키로 잠깐 바꾸면 된다.

키구분동작
1x00000000000000000000AA 사이트 키 항상 통과 (위젯 보임)
1x00000000000000000000BB 사이트 키 항상 통과 (위젯 안 보임)
3x00000000000000000000FF 사이트 키 매번 인터랙티브 챌린지(체크박스) 강제 표시
2x00000000000000000000AB 사이트 키 항상 차단

더미 사이트 키가 만든 토큰을 실제 운영 시크릿 키로 검증하면 실패하고, 반대로 실제 사이트 키를 더미 시크릿 키로 검증해도 실패한다. 체크박스 UI 확인이 끝나면 반드시 더미 키를 실제 키로 되돌려야 한다 (자세한 현재 상태는 운영 전환 전 확인 사항 참고).

비밀번호 자격증명 검증

문제 사항

비밀번호를 안전하지 않게 저장·비교하거나, 실패 응답이 계정 존재 여부를 흘릴 수 있다.

문제 사항 분석 — 초기 시딩 데이터 중 일부 계정은 N/A, FIREBASE$uid 같은 BCrypt 형식이 아닌 값을 password_hash에 갖고 있어, 그대로 비교하면 예외가 발생한다.

  • 평문 비밀번호 저장은 DB 유출 시 즉시 전체 계정 탈취로 이어짐
  • 형식이 안 맞는 해시에서 예외가 그대로 노출되면 "이 아이디는 존재하지만 처리 중 오류"라는 정보가 새어나감
  • "아이디 없음"과 "비밀번호 틀림"을 다른 메시지로 보여주면 계정 존재 여부를 스캔당할 수 있음 (계정 열거, user enumeration)
해결 방안

BCrypt 단방향 해시로만 비교하고, 실패 케이스를 전부 같은 결과로 통일했다.

  • 저장은 PasswordEncoder(BCrypt)로만 수행 — 원문 복구 불가능한 단방향 해시
  • matches() 호출을 try/catch로 감싸, 형식이 안 맞는 해시에서 예외가 나도 "불일치"로 처리
  • 아이디 불일치·비밀번호 불일치·계정 상태 문제를 전부 동일한 메시지("아이디 또는 비밀번호가 올바르지 않습니다")로 통일
HqAuthService.java / BranchFallbackLoginService.javaJava
// 형식이 안 맞는 해시(예: 시딩 중 남은 "N/A" 같은 값)에 matches()가 예외를 던져도 그냥 "불일치"로 처리한다
private boolean matches(String rawPassword, String storedHash) {
  try {
    return passwordEncoder.matches(rawPassword, storedHash);
  } catch (Exception e) {
    return false;
  }
}

토큰 서명 · 만료 검증

AdminTokenService.java
문제 사항

세션 저장소 없이도 "이 토큰이 진짜 서버가 발급한 것"인지 신뢰성 있게 확인해야 한다.

문제 사항 분석 — AdminTokenService는 DB나 메모리에 세션을 저장하지 않고, adminId + 만료시각을 그대로 담은 문자열을 토큰으로 발급한다(stateless). 이 방식의 핵심 위험은 "내용 위조"와 "만료된 토큰 재사용"이다.

  • 토큰에 담긴 adminId를 그대로 클라이언트가 들고 있는 구조라, 위조 방지 장치가 없으면 다른 계정으로 위장 가능
  • 만료 시각을 검증하지 않으면 탈취된 토큰이 영구히 유효해짐
해결 방안

HMAC-SHA256 서명과 만료시각 검사를 매 요청마다 수행한다.

  • 토큰 = payload(adminId:만료시각) + HMAC-SHA256(payload, 서버만 아는 비밀키) 서명값을 Base64Url로 인코딩
  • verify()에서 서명을 다시 계산해 대조 — 페이로드를 조작하면 서명이 안 맞아 즉시 거부됨
  • 만료시각(12시간)을 매 검증마다 확인해 초과 시 null 반환(=인증 실패로 처리)
AdminTokenService.javaJava
public Long verify(String token) {
  String raw = new String(Base64.getUrlDecoder().decode(token), ...);
  String[] parts = raw.split(":");
  if (!sign(payload).equals(parts[2])) return null; // 서명 불일치 → 위조
  if (Instant.now().getEpochSecond() > expiresAt) return null; // 만료
  return Long.parseLong(parts[0]);
}

이미지 업로드 — 경로 탐색(Path Traversal) 방지

HqUploadController.java HqUploadService.java WebMvcConfig.java
문제 사항

업로드된 파일을 사용자가 보낸 파일명으로 그대로 저장하거나, 그 파일명으로 다시 서빙하면 서버의 임의 경로를 읽거나 덮어쓸 수 있다.

문제 사항 분석 — HQ 관리자가 상품·맛 이미지를 올리는 POST /api/hq/uploads는 MultipartFile의 originalFilename을 받는다. 이 값은 브라우저가 보내주는 그대로라 클라이언트가 임의로 조작할 수 있는 입력이다.

  • 원본 파일명에 ../../../etc/passwd 같은 상대 경로가 섞여 있으면, 그 값을 그대로 저장 경로에 이어 붙였을 때 업로드 디렉터리 밖으로 빠져나가 임의 파일을 덮어쓸 위험(Path Traversal)
  • 원본 파일명을 그대로 저장하면 동시에 같은 이름으로 올린 다른 관리자의 파일을 덮어쓸 수 있음(파일 충돌)
  • 확장자를 검사하지 않으면 이미지가 아닌 실행 가능한 파일(.jsp, .php 등)이 웹이 서빙하는 디렉터리에 올라갈 위험
해결 방안

사용자가 보낸 원본 파일명은 확장자를 읽는 데만 쓰고, 실제 저장 파일명은 서버가 UUID로 새로 만든다 — 그러면 저장 경로에 사용자 입력이 전혀 섞이지 않아 경로 탐색 자체가 성립하지 않는다.

  • 확장자 화이트리스트(png·jpg·jpeg)만 허용, 그 외 확장자는 IllegalArgumentException으로 거부
  • 저장 파일명은 UUID.randomUUID() + "." + extension으로 서버가 직접 생성 — 원본 파일명 문자열은 저장 경로 조합에 아예 사용되지 않음
  • 파일 서빙은 자체 다운로드 API 없이 Spring의 ResourceHandlerRegistry 정적 리소스 핸들러(/uploads/**)로만 처리 — 상위 경로 접근을 자체적으로 차단하는 Spring 내장 로직을 그대로 신뢰
  • 업로드 엔드포인트는 HqAccessService.requireAdmin()으로 HQ 관리자만 호출 가능
HqUploadService.javaJava
private static final Set<String> ALLOWED_EXTENSIONS = Set.of("png", "jpg", "jpeg");

public String store(MultipartFile file) {
  // 원본 파일명은 확장자를 읽는 용도로만 쓴다 - 저장 경로 조합에는 절대 쓰지 않는다
  String originalName = file.getOriginalFilename() == null ? "" : file.getOriginalFilename();
  String extension = ...; // 마지막 "." 뒤 문자열, 소문자로 정규화
  if (!ALLOWED_EXTENSIONS.contains(extension)) {
    throw new IllegalArgumentException("PNG, JPG, JPEG 파일만 업로드할 수 있습니다.");
  }

  // 저장 파일명은 UUID로 새로 만든다 - 사용자가 보낸 이름/경로는 여기서 완전히 버려진다
  String filename = UUID.randomUUID() + "." + extension;
  Path target = Paths.get(uploadDir).resolve(filename);
  Files.copy(file.getInputStream(), target, StandardCopyOption.REPLACE_EXISTING);
  return "/uploads/" + filename;
}

// HqUploadService가 app.upload.dir에 저장한 파일을 /uploads/** 로 그대로 서빙한다
public void addResourceHandlers(ResourceHandlerRegistry registry) {
  String location = Paths.get(uploadDir).toAbsolutePath().toUri().toString();

따로 경로 검증 유틸을 만들 필요가 없었던 이유

일반적인 Path Traversal 대응은 "입력 경로를 정규화한 뒤 기준 디렉터리로 시작하는지 검증"하는 방어 코드(validateAndGetSafePath 같은 유틸)를 따로 둔다. 이 프로젝트는 그 대신 애초에 사용자 입력이 경로 조합에 들어갈 일을 없앴다 — 저장 시 파일명을 서버가 전부 새로 만들고, 서빙은 Spring 내장 정적 리소스 핸들러에 맡겼다. 공격 표면 자체를 지운 셈이라 더 단순하고 견고하다.

A01:2025  Broken Access Control

권한은 URL이 아니라
토큰에서 결정한다

수정 전branch/order/controller/BranchOrderController.java

public class BranchOrderController {

  @GetMapping

          @PathVariable Long branchId) {
    // URL에 담긴 값을 그대로 사용

수정 후같은 파일 + global/security/BranchAccessService.java
@RequestMapping("/api/branch/orders")
public class BranchOrderController {

  @GetMapping
  public List<...> getBranchOrders(
          @RequestHeader("Authorization") String auth) {
    // 토큰 주인이 담당하는 지점을 서버가 조회
    Long branchId = branchAccessService.requireBranchId(auth);
    return service.getBranchOrders(branchId);
  }
문제 — 1번 지점 관리자가 URL만 /api/branch/3/orders로 바꾸면 남의 지점 주문을 그대로 조회할 수 있었다.
해결 — URL에서 지점 번호를 아예 없앴다. 토큰을 검증해 담당 지점을 서버가 정하므로 조작할 값 자체가 없다.

    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

A02 상세  ·  frontend/nginx.conf

보안 헤더 6종,
각각 무엇을 막나

헤더적용한 값막는 것
Strict-Transport-Securitymax-age=31536000;
includeSubDomains		SSL-strip — 중간에서 HTTPS를 HTTP로 강등시켜 통신을 엿보는 공격. 브라우저가 1년간 이 도메인을 HTTPS로만 접속한다. 단, 현재 80 포트만 열려 있어 HTTPS 적용 후에 효력이 생긴다.
Content-Security-Policydefault-src 'self'
+ 실제 사용 도메인만 허용		XSS — 악성 스크립트가 삽입돼도 허용되지 않은 출처면 브라우저가 실행을 차단한다. 6종 중 가장 강력하고, 유일하게 우리 프로젝트를 조사해야 값이 나오는 헤더.
X-Frame-OptionsSAMEORIGIN클릭재킹 — 우리 로그인 페이지를 투명 iframe으로 감싸 사용자가 모르고 클릭하게 만드는 공격. CSP의 frame-ancestors와 함께 구형 브라우저까지 대응.
X-Content-Type-OptionsnosniffMIME 스니핑 — 업로드된 이미지 안에 숨겨진 스크립트를 브라우저가 오인해 실행하는 것. 이미지 업로드 기능이 있어 실질적 의미가 있다.
Referrer-Policystrict-origin-
when-cross-origin		URL 정보 유출 — 외부 사이트로 이동할 때 주문번호·관리자 경로가 담긴 전체 URL이 상대 서버 로그에 남는 것. 외부로는 도메인만 보낸다.
Permissions-Policycamera=(), microphone=(),
geolocation=(), usb=(), payment=()		불필요한 기능 악용 — 안 쓰는 브라우저 기능을 아예 꺼둬, XSS가 성공해도 카메라·마이크 접근 시도 자체가 차단된다.

값이 정해져 있어 넣기만 하면 되는 5개와 달리, CSP는 프로젝트가 실제로 붙는 외부 도메인을 전부 찾아내야 값을 쓸 수 있었다 — Turnstile · Toss Payments · Firebase Auth · 카카오 우편번호 4곳. 하나라도 빠뜨리면 해당 기능이 조용히 동작을 멈춘다.

민감정보는

수정 후OrderService.java · MobileNumberCrypto.java
// 저장 전에 두 가지로 변환 — 평문은 이 메서드를 벗어나지 않는다
String hash = MobileNumberCrypto.hash(rawMobileNumber);
customer = customerRepository.findByMobileNumberHash(hash)
    .orElseGet(() -> customerRepository.save(
        Customer.builder()
            .mobileNumberHash(hash)                            // 조회용
            .mobileNumberMasked(MobileNumberCrypto.mask(rawMobileNumber))
            .build()));                                        // 010****5678

// MobileNumberCrypto
public static String hash(String plain) {   // SHA-256 → 64자 hex
    return HexFormat.of().formatHex(
        MessageDigest.getInstance("SHA-256")
            .digest(plain.getBytes(UTF_8)));
}
public static String mask(String plain) {   // 앞3 + **** + 뒤4
    return plain.substring(0,3) + "****" + plain.substring(7);
}
문제 — 입력받은 번호를 변환 없이 그대로 넘겨 DB에 평문으로 쌓였다. DB가 유출되면 전화번호가 그대로 노출되고, 백업 파일·관리 도구 화면에서도 평문이 보인다.
해결 — 저장 직전에 조회용 해시와 표시용 마스킹 두 값으로 변환한다. 해시는 같은 번호면 항상 같은 값이라 WHERE 조회가 되고, 평문은 이 메서드를 벗어나면 어디에도 남지 않는다.

A06:2025  Insecure Design

코드가 아니라
설계가 잘못된 경우

구현 결함 (나머지 9개 항목)

설계는 맞는데 코드를 잘못 짠 것. 파라미터 바인딩을 쓰기로 해놓고 한 곳에서 문자열을 이어붙인 경우 등.

→ 그 코드를 고치면 해결된다.

설계 결함 (A06)

코드를 완벽하게 구현해도 안전하지 않은 것. 필요한 방어가 애초에 설계에 없었던 경우.

→ 설계를 바꿔야 해결된다.

판별 기준은 하나다 — "이 코드를 버그 없이 완벽하게 구현하면 안전해지나?" 아니라면 설계 결함이다. 이번에 추가한 주문 수량 제한이 정확히 그 사례로, 상한이 없던 것은 코드 버그가 아니라 제한을 둔다는 발상이 설계에 없었던 것이다.

해결 — 상한을 설계에 추가했다. 함께 관리자 토큰의 5가지 공격 시나리오를 테스트로 재현해 전부 거부되는지 검증했다.

문제 — 로그가 콘솔에만 남아 서버를 재시작하면 사라졌다. 침해 사고가 나도 무슨 일이 있었는지 확인할 근거가 없다.
해결 — 일자별 파일로 30일간 보관하고, 같은 설정에서 개행 문자까지 제거해 로그 위조도 함께 막는다.
A10:2025  Mishandling of Exceptional Conditions

예외는 삼키지 않고,
내부 정보는 흘리지 않는다

수정 전global/exception/GlobalExceptionHandler.java
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<Map<String, String>> handleBadRequest(
        IllegalArgumentException e) {
    // 로그 기록 없음
    return ResponseEntity.badRequest()
        .body(Map.of("message", e.getMessage()));
    // 내부 예외 메시지를 클라이언트에 그대로 전달
}
수정 후같은 파일
@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<Map<String, String>> handleBadRequest(
        IllegalArgumentException e) {
    log.warn("잘못된 요청 처리 중 예외가 발생했습니다.", e);  // 상세는 로그에만
    return ResponseEntity.badRequest()
        .body(Map.of("message", "잘못된 요청입니다."));  // 응답은 일반화
}
문제 — 내부 예외 메시지가 그대로 응답에 실려 테이블·컬럼명이나 내부 로직이 노출될 수 있었다. 게다가 로그도 남지 않아 원인 추적이 어려웠다.
해결 — 클라이언트에는 일반화된 문구만 보내고 상세 원인은 서버 로그에만 남긴다.

A06

위협 모델 문서화

보안 요구사항(S-087 등 6건)과 항목별 대응책은 정리돼 있으나, 자산 · 공격자 · 공격 경로를 한 장으로 묶은 위협 모델 문서는 아직 없다. 새 기능을 설계할 때 이 문서를 먼저 갱신하는 절차를 넣는 것이 다음 단계다.

운영

HTTPS 적용이 선행되어야 완성되는 항목

HSTS 헤더는 이미 넣었지만 현재 nginx는 80 포트만 열려 있어 실제 효력이 없다. 로드밸런서나 CDN에서 TLS를 종료하도록 붙이면 그 시점부터 동작한다.

검증

CSP 실환경 확인

Turnstile · Toss · Firebase · 카카오 우편번호 4개 플로우를 배포 환경에서 실행해 브라우저 콘솔에 CSP 위반이 없는지 확인해야 한다. 로컬 개발 서버는 nginx를 거치지 않아 검증되지 않는다.
